## R-001 详解：`get_tool` 返回 dict

**问题**：`tools/_base.py` 中 `get_tool(name) -> Optional[dict]`，返回 `{func, schema, group, streamable}`。
原方案当作 callable 直接调用，会触发 `TypeError: 'dict' object is not callable`。

**修复**：
```python
# 错误写法（v1.0）
tool_func = get_tool(tool_name)
result = await tool_func(**params)  # TypeError

# 正确写法（v2.0）
meta = get_tool(tool_name)
if not meta or "func" not in meta:
    return json.dumps({"error": f"工具 {tool_name} 不存在", "step": i + 1})
tool_func = meta["func"]
result = await tool_func(**params)
```

## R-002 详解：sync / async 分支

**问题**：`asyncio.to_thread(func, **params)` 期望 func 是同步函数。
若 func 是 async 函数，`to_thread` 会返回 coroutine 而不执行；后续 await 报错。

**修复**：
```python
if asyncio.iscoroutinefunction(tool_func):
    result = await tool_func(**params)
else:
    result = await asyncio.to_thread(tool_func, **params)
```

## R-003 详解：原子工具必须 `@with_owner`

**问题**：组合工具内部走 `execute_workflow_steps` → `tool_func(**params)`。
如果 tool_func 没有 `@with_owner` 装饰器，`_owner_id` 参数虽然传了但工具内部拿不到，会用空 owner 查数据 → 跨用户数据泄漏。

**修复**：P0 验收标准要求所有被组合工具调用的原子工具（filter_content / cluster_related / extract_slots / generate_itinerary / compare_opinions / analyze_sentiment / query_report / push_report）必须带 `@with_owner`。

## R-004 详解：step_N 索引正则化

**问题**：原代码 `results.get(f"step_{parts[0][-1]}", {})`，对 `"step_10_result"` 取 `parts[0][-1]` = `"0"`，错解析为第 0 步。

**修复**：
```python
_STEP_IDX_RE = re.compile(r"^step_(\d+)$")

def _resolve_step_index(token: str) -> Optional[int]:
    m = _STEP_IDX_RE.match(token.strip())
    return int(m.group(1)) if m else None
```

## R-005 详解：模板匹配线程池 + UPSERT + enabled=1

**问题 1**：模板匹配 Jaccard 计算（jieba 切词 + 遍历候选）阻塞事件循环，无法被 cancel。
**修复**：用 `loop.run_in_executor(None, _match_workflow_template_sync, ...)` 放线程池。

**问题 2**：auto_template 累积若不强制 `enabled=1`，会被 `WHERE enabled=1` 过滤掉，模板永远不命中。
**修复**：`upsert_auto_template()` INSERT 和 UPDATE 都强制 `enabled=1`。

**问题 3**：用 `INSERT OR IGNORE` 不会更新 hit_count。
**修复**：先 SELECT，再判断 INSERT 或 UPDATE hit_count++（UPSERT 语义）。

## R-006 详解：_maybe_adjust_plan 不是 generator

**问题**：原方案写 `async for chunk in _maybe_adjust_plan(...): yield chunk`。
但 `_maybe_adjust_plan` 定义是 `async def`，不是 `async def + yield`。
触发 `TypeError: 'coroutine' object is not async iterable`。

**修复**：
```python
async def _maybe_adjust_plan(step_result, step_idx, ctx) -> Optional[str]:
    ...
    return emit_plan_adjusted(ctx.plan)

# 调用方
adjusted_chunk = await _maybe_adjust_plan(step_result, step_idx - 1, ctx)
if adjusted_chunk:
    yield adjusted_chunk
```

## R-007 详解：AgentContext 字段扩展

**新增字段**：
- `adjustment_count: int = 0` — P3 调用 `ctx.plan.get("adjustment_count", 0)` 不再每次都走默认值
- `user_intervened: bool = False` — 用户中途追加消息时置 True，阻止 auto_template 累积错误模式
- `workflow_id: Optional[int] = None` — P4 mode=scheduled 时由 `_persist_workflow` 写入

## R-008 详解：进度 hint 不入 current_messages

**问题**：原方案每轮 `ctx.current_messages.append(hint)`。
6 轮迭代 → current_messages 多 6 条 system message，污染 LLM 输入。

**修复**：
```python
plan_hint = {...} if plan else None
messages_for_llm = list(ctx.current_messages)  # 浅拷贝
if plan_hint:
    messages_for_llm.append(plan_hint)

# LLM 调用传 messages_for_llm（不修改 ctx.current_messages）
```

## R-009 详解：主循环不重复 criticality

**原因**：OpenAI Function Calling 不支持 LLM 传自定义字段（如 `criticality`）。
主循环 LLM 选工具后无法知道这个工具的 criticality。
criticality 三级行为仅在 `execute_workflow_steps`（组合工具路径）实现。

## R-010 详解：scheduled 工作流创建后不自动执行

**问题**：用户问"每天早上 9 点扫一下理想"，如果立即执行，会消耗一次爬虫 quota。
**修复**：phase_plan 检测 `mode=scheduled` → `_persist_workflow()` 落库 → emit `done_with_message` 让用户确认。
用户额外说"立即执行工作流 N"才触发 `manage_workflow(action="run_now")`。

## R-011 详解：trace_id + Semaphore(4)

**问题 1**：scheduler 跑在独立线程，ContextVar 不自动传播 → `_run_daily_summary` 同类问题已在 v2.2 修复，需沿用。
**修复**：`_run_user_workflows` 入口 `set_trace_id(generate_trace_id())`。

**问题 2**：5 个同时到点的 cron 同时起 5 个 asyncio task，可能打爆 LLM quota。
**修复**：`_WF_SEMAPHORE = asyncio.Semaphore(4)` 限流。

## R-012 详解：cancel API owner 校验

**完整路径**：`/api/agent/workflows/{wf_id}/cancel`（前缀 `/api/agent`，与现有 api.py 一致）。

**校验逻辑**：
```python
wf = db.get_by_id(workflow_id)
if wf["owner_id"] != owner_id and wf["owner_id"] != "system":
    raise HTTPException(403, "无权操作他人工作流")
```

Admin 特权版（`/api/admin/agents/workflows/{wf_id}/cancel`）不走 owner 校验。

## R-013 详解：list_workflows SQL 含 preset

**旧 SQL**：`WHERE owner_id=? AND source IN ('user','auto_template')` — 漏掉 preset。
**新 SQL**：`WHERE (owner_id=? AND source IN ('user','auto_template')) OR (source='preset')`。

## R-014 详解：save_as_preset 限定方向

**越权风险**：用户 A 创建 user 工作流 → `save_as_preset` → source 改 'preset' → 污染全局。
**修复**：仅允许 `auto_template → user` 方向；user → preset 必须 Admin 手动改 DB。

## R-015 详解：scheduler 跨线程 ContextVar

**问题**：scheduler 线程是新 asyncio loop，ContextVar 默认不在新 loop 中。
`with_owner` 装饰器从 contextvar 取 owner_id，取到 None → 抛 `OwnerRequiredError`。

**修复**：
```python
from backend.services.agent_service.tools._owner import (
    set_current_owner, reset_current_owner,
)
token = set_current_owner(owner_id)
try:
    # 调组合工具
    ...
finally:
    reset_current_owner(token)  # 必须配对！
```

## R-016 详解：Prometheus label

**问题**：`Histogram("...", labels=["workflow_id"], ...)` 会导致每条工作流对应一条 histogram。
若有 1000 个工作流 → 1000 条 histogram → Prometheus 存储爆炸，查询极慢。

**修复**：
```python
WORKFLOW_EXECUTIONS_TOTAL = Counter(
    "workflow_executions_total", ...,
    ["status"]  # 只保留 status，去掉 workflow_id
)
```

## R-017 详解：ALTER TABLE 幂等

**SQLite 限制**：3.35 之前不支持 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`。

**修复模式**：
```python
for col, decl in [("workflow_total", "INTEGER DEFAULT 0"), ...]:
    try:
        cursor.execute(f"ALTER TABLE agent_health_snapshot ADD COLUMN {col} {decl}")
    except Exception:
        pass  # 已存在则跳过
```

已在 `memory_store.py:90` 验证可行。
